# MixLab Rollback Runbook（Phase 3 准备版）

> 状态：Round5 起草，未在真实环境演练。演练必须在隔离环境/合成数据上执行，禁止在真实 NAS/用户工作区演练。
> 原则：先止损（停止新写入与新发布），再保留证据，最后回滚；任何"手工改发布指针/手工改库文件"都是禁止操作。
> 与发布列车配套：docs/operations/release-trains.md、scripts/release/versions.json（rollback_triggers）、发布清单 release-manifest.json。

## 1. 决策矩阵

| 现象 | 级别 | 先做 | 回滚范围 | RTO 目标 |
|---|---|---|---|---|
| 数据丢失/错误覆盖已完成素材/公共库被删 | P0 | 立即停止发布与 worker；隔离现场 | 服务镜像/静态资源 + 指针；不覆盖用户成果 | 30 分钟内恢复只读可用 |
| 发布指针异常、剪辑端读不到或读错版本 | P0 | 停止发布新版本；记录指针/清单 | 发布指针回上一已验证版本 | 15 分钟内指针可解析 |
| 管理端登录/权限/错误契约异常 | P1 | 关闭新 flag；采集 401/错误码样本 | admin-web/admin-api 镜像 | 30 分钟 |
| Windows 桌面安装失败/崩溃率超阈值 | P1 | 撤回下载入口/标记候选不可用 | 安装包回上一版；工作区备份恢复 | 60 分钟（含通知） |
| 契约/库格式非加法变更或兼容错误率上升 | P1 | 停止列车；冻结发布 | 客户端/服务端代码回滚，数据保持兼容 | 60 分钟 |
| 身份/事件 service 模式异常 | P1 | feature flag 关闭新路径 | 切回 legacy 共享文件模式（先排空 service 写入） | 30 分钟 |
| 迁移脚本失败/中断 | P0/P1 | 停止迁移；保留迁移日志与备份 | 前向修复优先；未完成权威切换前才允许恢复备份 | 视数据量 |

## 2. 回滚前置条件（发布前必须确认）

1. 上一版本发布清单（JSON/Markdown）与 rollback_target（格式 `<commit>+<artifact_sha256>`，dirty 工作区附 " (dirty)"）已归档；镜像 digest/安装包 SHA 可查。若 rollback_target 带 dirty 标记，说明发布时的 commit 不能单独复现制品，必须同时按记录的 artifact_sha256 找到对应构建产物。
2. 发布指针（current-release.json 及 release 目录）备份可用；不得只备份指针而丢发布目录。
3. 管理端 worker/supervisor 状态可停可控；确认没有正在执行的发布/恢复命令。
4. 服务模式迁移（accounts_service/usage_service）若涉及权威存储切换：旧写入者已停止、outbox 已排空或有可恢复记录；数据库/WAL 有一致性备份（进程退出后备份）。
5. Windows 桌面：安装包保留上一版；用户工作区备份策略与恢复说明已通知。
6. 通讯：发布负责人、值班、数据负责人知情；确认回滚窗口与不可用时间。

## 3. 分组件回滚步骤

### 3.1 admin-web 静态资源/镜像
1. 停止发布列车与后续构建；记录当前失败清单与镜像 tag/digest。
2. 将 admin-web 容器回退到上一已验证 image digest（或上一版 nginx 静态包），不改动库根目录与 .mixlab-library 数据。
3. 验证：/health 200、登录、/api/v1/capabilities（若启用）、首页/素材处理/设置可加载；浏览器缓存按需清空（静态资源文件名带 hash 时通常无需强制清）。
4. 记录：回滚前后 digest、验证截图/日志；通知使用者。

### 3.2 admin-api / admin-worker 服务
1. 先停 worker（避免继续写入），保留 supervisor 日志；确认没有执行中的发布/恢复命令（操作记录页）。
2. 回退 admin-api 镜像到上一版本 digest；worker 回到与 API 同版本镜像。
3. 若上一版本不读取新库字段：不要回滚库数据；只回滚二进制。新增字段保持向后兼容（契约/库格式只加法）。
4. 验证：/health、/ready、登录、素材列表、操作记录、发布门禁；观察错误率与慢请求。
5. 若存在未完成的迁移脚本：停止迁移进程，按 3.7 处理，不得直接回退库。

### 3.3 发布指针（index / current-release）
1. 停止发布 worker 与手动上线操作，记录当前指针内容、目标目录、release 清单哈希。
2. 用既有发布恢复/校验工具把指针回切到上一已验证版本；禁止直接编辑 current-release.json（若工具缺失，先把证据与回滚方案上报，再按审批执行受控操作）。
3. 校验：指针可解析、目标目录完整、剪辑端能读到上一版本；损坏/不完整的新发布目录保留现场（隔离），不要删除。
4. 记录：指针回滚前后内容、校验命令输出、剪辑端验证结果。

### 3.4 剪辑端 Windows 桌面
1. 撤回/标记安装包候选不可用；通知用户暂停升级。
2. 发布上一版安装包（SHA 与归档核对）；提供工作区备份恢复说明；不重复使用同一应用状态目录并行运行两个版本。
3. 验证：安装/卸载/升级/回滚四条路径；旧版读取当前发布指针正常；历史任务可打开。
4. 记录：安装包版本/SHA、验证机器、四路径结果。

### 3.5 智能剪辑端（smart）
1. 回退 smart Web/桌面到上一版本；关闭 smart beta flag。
2. 检查 Python runtime/本地 API 健康与 token/confirm 行为（若启用）；确认候选线不影响管理端与剪辑端交付线。
3. 验证：候选主流程可用或明确标记不可用；隔离数据处理。

### 3.6 contracts / library-format
1. 契约与库格式**只允许加法演进**；已发布的格式不能真正回滚，只能回滚消费者（客户端/服务端代码）并保持数据兼容。
2. 若新代码依赖新字段：回滚代码到兼容旧数据的版本；不要回滚已写入的新字段数据。
3. 若必须删除字段/改变语义：停止列车，走 major 评审 + 旧客户端兼容期，禁止直接 hotfix 回滚。
4. 验证：旧客户端可读新数据；错误码映射/能力发现回退到旧路径；记入发布说明。

### 3.7 迁移脚本与身份/事件服务（service 模式）
1. 停止迁移与所有旧/新写入者；导出/记录迁移状态、outbox 与失败项。
2. 仅当**权威存储尚未切换到 service 模式**且增量写入可对账时，才允许从一致性备份恢复；若已切换，优先前向修复或切回 legacy 双读校验，不得用旧备份覆盖新数据。
3. 切回 legacy 模式（feature flag/env 关闭 service 路径）后：验证登录、账号状态、事件补报（outbox）、管理端操作记录；确认只有单一权威存储。
4. 记录：迁移脚本版本/参数/日志、切回时间、数据对账结果。

## 4. 回滚后验证清单

- [ ] /health、/ready 返回正常；关键错误码仍为契约 v1 兼容（AUTH_REQUIRED 等）。
- [ ] 发布指针可解析；剪辑端读到的版本与回滚清单一致。
- [ ] 管理端登录、素材列表、预处理状态、发布门禁、设置读取正常；写入操作按需暂停。
- [ ] 已完成素材/用户成果未被覆盖；发布目录与库目录只读校验通过。
- [ ] 新能力 flag 均处于关闭状态；旧路径可用。
- [ ] 证据归档：回滚前后清单、镜像 digest/安装包 SHA、指针内容、日志、验证记录、负责人签字。

## 5. 演练清单（季度）

| 场景 | 频率 | 环境 | 验收 | 负责人 |
|---|---|---|---|---|
| admin 镜像回滚 | 每季度 | 隔离 compose | 30 分钟内恢复只读可用，证据齐全 | 发布负责人 |
| 发布指针回滚 | 每季度 | 合成库 + 临时 release | 指针可解析且剪辑端读到上一版 | 数据负责人 |
| Windows 安装包回滚 | 每半年 | 空闲 Windows 机 | 安装/卸载/回滚四路径 + 旧版可用 | 剪辑端负责人 |
| service 模式切回 legacy | 每季度（flag-on 前必做） | 隔离库 + 合成账号/事件 | 无双写、登录与补报正常、无数据丢失 | 身份/事件服务负责人 |
| 契约 major 兼容演练 | 每半年 | 隔离三仓 | 旧客户端可读、错误码映射回退正常 | 契约负责人 |

演练不得使用真实 NAS、真实用户或生产发布指针；演练结果写入发布列车记录并在 Phase 3 启动前复核。

## 6. 回滚限制与禁止事项

- 禁止手工编辑发布指针、库清单或 .mixlab-library 关键文件作为"快速回滚"。
- 禁止用陈旧备份覆盖迁移后产生的新账号/权限/事件数据；权威存储切换后必须先对账再决定。
- 禁止删除失败版本目录、用户作品、日志与现场证据；失败版本应隔离保留用于诊断。
- 禁止在用户正在剪辑的机器上强制结束应用或并行运行新旧版本。
- 禁止把回滚当作"修复"：回滚后必须在发布记录中登记根因、影响范围与后续修复任务。
