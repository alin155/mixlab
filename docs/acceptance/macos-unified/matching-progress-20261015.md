# 原声匹配实际进度

## 为什么等待较久

旧页面仅显示“正在检索真实原声片段”，没有后端阶段信息，不能凭这句话判断正在同步、计算还是等待。

当前链路为：读取管理端发布 → 同步并锁定本机快照 → 按句文字检索 → 核对实际素材 → 未精确命中时调用语义检索 → 完成审核方案。

现场有两类准备成本：

- 本机正在建立 `v012698` 的语义索引，共 1,292,565 段。管理端发布的是转写和文字检索索引；近似表达检索还需要本机额外计算语义向量。
- 管理端继续发布新版本，作品生成会先同步当时的版本。安装后实测该作品处于 `snapshot_sync`，先后观察到 v012713、最终 v012714；3 句尚未进入逐句检索。这是实机阶段证据，不能把所有耗时都归到语义计算。

现有 AI 工作进程串行处理；语义检索会先等已有建索引任务。每个发布快照的向量文件独立，新版本未就绪时仍需建立对应索引。因此短文案也可能长时间等待，等待成本不只取决于文案长度。

## 本次实现

- 作品增加可选的实际进度，兼容已有数据，不改数据库 schema：开始时间、当前阶段、快照版本、当前句、已完成句数，以及精确/近似/缺句统计。
- 在真实操作边界更新阶段：检查快照、同步快照、快照就绪、文字检索、素材核对、等待另一快照索引、建立当前索引、语义检索及完成/失败。
- 索引数量来自正在运行的 AI 任务；接口读取时合并最新计数，避免每一批向量都额外写一次作品数据库。区分作品快照和后台索引快照，不把另一版本的百分比算作本作品匹配完成比例。
- 页面显示已用时、已完成事项、逐句结果和适用阶段的索引数量。没有文件复制数量或可靠 ETA 的阶段不虚构百分比及倒计时。
- 从作品列表重新打开匹配中的作品直接进入进度页；切回列表不停止后台任务。

本批只增加可观测进度与返回路径，不改变召回、匹配或索引计算策略。
