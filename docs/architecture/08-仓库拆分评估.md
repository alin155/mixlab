## 2. 目标架构（推荐：混合模式，分两阶段）

### 目标仓库拓扑

    platform 仓（平台仓，保留跨边界契约与纯共享库）
      packages/contracts          # CONTRACT_VERSION / CONTRACT_ERRORS / CapabilityTableV1 / ReleaseManifestV2 / EventEnvelopeV1 / LocalAgent v1
      packages/library-format     # 公共库/发布目录磁盘格式
      packages/service-clients    # 身份/事件/发布服务客户端（默认关闭 flag）
      packages/protocol           # 三端共享协议常量
      packages/runtime-config     # 运行配置键/加载规则
      docs/architecture/{06,07,08,...}、docs/spec-traceability.md
      scripts/release/            # 版本表/发布清单生成器（跨产品发布列车共用）
      .github/workflows/contracts.yml（契约测试 + 三仓 hash 校验）

    admin 产品仓（管理端主线）
      apps/admin-web
      packages/admin-api, admin workers（scripts/workers）, preprocess-core/asr-core/oss-core/doctor-core
      packages/library-fs（服务端共享状态；拆分前期仍在 admin 仓，见 §4 不迁项）
      search-core/search-sqlite/searchd、windows-test-runner、ui-foundation
      cutter-web/cutter-desktop 不再保留副本（改由 cutter 产品仓权威）
      .github/workflows：admin typecheck/test、docker-admin、events/account 服务

    cutter 产品仓（剪辑端交付线）
      apps/cutter-web, apps/cutter-desktop, packages/cutter-api, packages/cutter-local, packages/ffmpeg-core, scripts/desktop, scripts/servers/cutter-api-server.ts
      .github/workflows：cutter typecheck/test + Windows 安装包

    smart 产品仓（智能剪辑候选线，flag 默认关）
      apps/smart-cutter-web/desktop, packages/smart-cutter, scripts/smart-cutter, scripts/servers/smart-cutter-api-server.ts
      .github/workflows：smart typecheck/test + Windows 安装包

### 依赖方向

产品仓 → 平台仓（只读依赖，经私有 registry 或 git subtree 固定版本）；平台仓不依赖任何产品仓。目标是**平台包只允许加法演进**（07），产品仓按版本列车上车。

## 3. 三个方案的比较

| 方案 | 描述 | 收益 | 成本/风险 | 结论 |
|---|---|---|---|---|
| A. 维持三份 monorepo 副本 | 现状 | 零迁移成本；历史保留 | 共享包漂移（library-fs 已发生）、三份 CI 重复、权限无法按团队收口、契约同步靠手工、三仓分支继续分叉 | 仅作为过渡，不可长期 |
| B. 收敛为单一 monorepo + release trains | 以 admin 仓为主线合并 cutter/smart 分叉；一个 CI；CODEOWNERS 分团队；产品按 tag/版本表发布 | 立即消除复制/漂移/重复 CI；契约单一源；最快、风险最低；保留 git 历史（合并而非重写） | 需合并分叉（4/11 提交与 smart +8）、CI 时长增加、产品独立发布需 release trains 纪律（已具备）、权限边界依赖 CODEOWNERS | **第一阶段推荐（1-2 周工作量）** |
| C. 混合：平台仓 + 3 产品仓 | 平台仓含 contracts/library-format/service-clients/protocol/runtime-config（+ 发布工具）；产品仓各自应用与运行时依赖，经私有 npm registry/subtree 固定平台包版本 | 平台独立发布、产品独立 cadence、权限与 CI 收敛到各自仓库、契约有唯一源 | 需发布平台包（本轮约束不 npm install，需 Round7 引入 registry 或 subtree）；跨仓 PR/版本矩阵/兼容测试成本；Windows 打包引用路径变化；一次性迁移 4-6 周 | **第二阶段推荐（B 稳定后执行）** |

推荐路线：**先 B 后 C**。B 把“复制 + 手工同步 + 重复 CI + 无法按团队授权”四个最大问题在 1-2 周内收敛；随后在稳定 monorepo 上做 C 的平台包拆分（4-6 周），避免在漂移状态下直接拆仓导致三方历史与未提交工作混在一起。

## 4. 迁移步骤（分阶段，暂不执行）

### Phase B：monorepo 收敛（Round7 候选）

1. **冻结与备份**：三仓各自打 annotated tag（含当前 dirty 补丁导出），确认 release 列车停车；按 docs/operations/git-checkpoints.md 建立 checkpoint。
2. **收敛 dirty**：把三仓未提交改动按归属导出为补丁/分支提交（admin 1419、cutter 61、smart 32）；验收产物移入 docs/acceptance 或忽略清单，不作为发布依据。
3. **合并分叉**：以 admin 主线为基线，cutter 的 4 个自有提交与 smart 的 8 个提交按主题 cherry-pick/merge；冲突点集中在 apps 与平台包（library-fs 已漂移），逐文件按权威源合并并跑三端测试。
4. **CI 收敛**：保留 admin/cutter/smart 三组 job matrix（路径过滤），共享 typecheck/test 缓存；Windows 打包按产品保留独立 workflow；平台契约测试独立 job。
5. **治理生效**：启用 CODEOWNERS/分支保护（06 §3）；契约 hash 检查进 required checks。
6. **发布列车切换**：docs/operations/release-trains.md 的 weekly/biweekly/monthly 列车改从单一 monorepo 出包（tags 保留产品边界）。
7. **验证门禁**：三端全量测试绿 + release:check PASS + 一次隔离环境安装/回滚演练；独立验证后关闭旧仓写入（只读归档）。

### Phase C：平台仓拆分（B 稳定后）

1. **包边界定稿**：契约委员会确认平台包清单（contracts/library-format/service-clients/protocol/runtime-config + release 工具）与版本策略（07），明确 library-fs 等 server-side 共享库暂留 admin 产品仓。
2. **发布通道**：二选一——私有 npm registry（GitHub Packages，推荐，需要 repo-admins 开权限与 CI token）或 git subtree/submodule 固定 SHA（无外部依赖、本轮约束下可行，但升级繁琐）。本轮约束（不安装新依赖）下不建议实际执行，方案文档先定。
3. **建立平台仓**：从 monorepo 抽离平台包（保留 git 历史用 git filter-repo 或直接新仓+首个快照提交，后者更简单）；CI 仅跑契约测试 + hash/版本检查 + 包发布。
4. **产品仓接入**：产品仓移除平台包副本，改为锁定版本依赖；CI 增加平台版本兼容矩阵；CODEOWNERS 指向平台团队。
5. **契约同步机制退役**：三仓手工镜像改为“平台包版本 + contracts:check”，06 §5 的过渡机制删除。
6. **回退**：保留 monorepo tag 与旧仓只读；如需回退，产品仓重新 vendor 平台包并恢复 monorepo 分支，数据/发布指针不受影响。

## 5. 不迁移项（明确保留/不动）

1. **用户数据与权威状态**：公共素材库、`.mixlab-library`（发布指针/releases/indexes/账号/事件/审计）、NAS 布局、用户工作区——仓库拆分不影响数据路径；发布指针与迁移由 release/rollback 文档管理。
2. **服务进程与端口**：admin-api / cutter-api / smart-cutter-api / cutter-account-service / usage-service 的进程模型与 loopback 端口不变；账号/事件服务默认关闭 flag 不在拆分中改变。
3. **验收证据与运行产物**：docs/acceptance 产物、Round1-6 gate 证据（progress/ROUND*-GATE.md 在外部工作区）保持原位；不随 git filter 历史拆分而丢失（另存清单）。
4. **Windows 安装包与签名资产**：安装包构建在各自产品 CI 内，签名证书/密钥留在受控 secret 存储，不进任何仓库。
5. **CI secrets/Environments/分支保护配置**：平台不在仓库代码内迁移，按 06 的 admin 清单重建。
6. **历史提交**：不做多仓历史重写；平台仓用首个快照提交起步，旧 monorepo tag 永久保留作为审计/回退点。

## 6. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 三仓 dirty 工作丢失/混入 | 高（1419+61+32 项含未交付修复） | Phase B 第 2 步先导出补丁/tag；每步校验 git status 与测试 |
| 分叉合并冲突（library-fs 已漂移） | 中高 | 以 admin 为基线 + 契约委员会逐文件裁决；先合平台包再合 apps；冲突文件列入清单评审 |
| 契约版本错配（产品仓锁定旧平台包） | 中 | 07 兼容矩阵 + 平台版本/最低客户端版本；CI 检查 |
| CI 时长与成本 | 中 | 路径过滤 matrix、缓存、平台/产品 job 拆分；Windows 打包按产品独立 |
| 权限/团队配置缺失（CODEOWNERS 未生效） | 中 | 06 §3 前置清单；生效前不宣称强制 |
| 拆分后跨仓联调变慢 | 中 | 平台包发布列车 + 夜间兼容测试 + 预发环境 |
| 回退不完整 | 高 | 每阶段独立 tag/checkpoint + rollback-runbook 演练；数据层不在拆分范围 |

## 7. 时间估算（建议，非承诺）

| 阶段 | 内容 | 工时 |
|---|---|---|
| B0 | 冻结/checkpoint/导出 dirty 补丁 | 1-2 天 |
| B1 | 分支合并与冲突解决 + 三端测试绿 | 3-5 天 |
| B2 | CI 收敛 + CODEOWNERS/分支保护 + release:check 门禁 | 2-3 天 |
| B3 | 发布列车切换 + 隔离环境演练 + 独立验证 | 2-3 天 |
| C1 | 平台包边界与发布通道（registry/subtree）决策与试点 | 1 周 |
| C2 | 平台仓建立 + 包发布 + 产品仓接入 | 2-3 周 |
| C3 | 兼容矩阵/回滚演练/旧仓只读归档 | 1 周 |

合计：Phase B 约 1.5-2 周；Phase C 约 4-6 周（依赖 registry 决策与三端联调窗口）。

## 8. 决策门与建议

1. **建议 repo-admins + 契约委员会在 Round6 Gate 后尽快批准 Phase B**（单 monorepo + release trains + CODEOWNERS），这是消除漂移的最低成本路径。
2. Phase C 的前置：平台包发布通道决策 + 契约委员会批准平台包清单 + 至少一个产品仓试点（建议 cutter 先接平台包，因其 Windows 打包链最独立）。
3. 未获批准前保持三仓现状，但必须用 06 §5 的 contracts hash 检查与 07 的契约审批止血，不允许继续手工“改一处抄三处”。
4. 任何拆分动作不得触碰 §5 不迁移项；数据迁移与服务权威切换继续按各自 runbook 独立评审。
