1. **不是三个“产品子仓”，而是同一 monorepo 的三份全量副本**：三个仓都含 admin-web、cutter-web、cutter-desktop、ui-fixtures 等全部 apps；smart 仓额外多 smart-cutter-web/desktop。
2. **历史分叉**：admin 与 cutter 的公共祖先是 fe5196c；cutter 有 4 个自有提交、admin 有 11 个自有提交（双向分叉）。smart 的 f525c0e 是 admin HEAD 的后代（含 admin HEAD + 8 个 smart 提交）。
3. **共享包物理复制**：protocol、library-format、service-clients、search-sqlite 在三个仓中逐字节相同（当前一致）；但 library-fs/src/index.ts 已是三份不同内容（已开始漂移）——证明复制方式不可持续。
4. **契约包**：packages/contracts（7 个文件）三仓逐字节一致（Lead 手工同步）；scripts/release/versions.json 在 admin 仓（Round5 发布工程）。
5. **CI 重复**：admin/cutter 的 .github/workflows 4 个文件逐字节相同；smart 多一个 smart-cutter-windows.yml；每个仓各跑一遍 npm ci + 全 workspace typecheck/test。
6. **无治理设施**：三仓均无 CODEOWNERS、无 PR 模板、无 ADR 目录、无分支保护声明（平台侧配置不可从代码验证）。

## 2. 目标所有权模型

| Owner 组 | 职责 | 典型路径 |
|---|---|---|
| repo-admins（仓库管理员） | 仓库设置、分支保护、CODEOWNERS 自身、组织级安全策略、权限审计 | CODEOWNERS、.github/、仓库 Settings |
| platform-core（平台核心） | 跨产品共享包与运行库、架构/治理文档、平台级兼容性 | packages/contracts 外的平台包、docs/architecture/ |
| contract-committee（契约委员会） | contracts/library-format/service-clients 等跨边界契约的加法演进审批（见 07） | packages/contracts、packages/library-format、packages/service-clients、versions.json |
| release-engineering（发布工程） | CI/workflows、发布列车、版本表、发布与回滚执行、Windows 打包流水线 | .github/、scripts/release/、docs/operations/、scripts/docker/ |
| security-reviewers（安全评审） | 认证/账号/密钥/边界安全的第二评审 | admin-users、cutter-users、cutter-account-*、admin-auth-*、服务进程与 ops 脚本 |
| admin-team / cutter-team / smart-team | 各自产品 app/API/桌面/验收；产品权威提交回到对应仓 | apps/admin-web、apps/cutter-*、apps/smart-cutter-*、产品专属 packages/scripts |

三仓各自的 CODEOWNERS 模板已放在仓库根：`CODEOWNERS`（2026-10-27 起草）。规则采用“最后一个匹配生效”，产品规则位于平台规则之后；跨边界契约路径要求 contract-committee；安全路径要求 security-reviewers 第二评审。

## 3. CODEOWNERS 生效前置清单（需用户/组织管理员确认并操作）

以下事项**无法由代码完成**，需 GitHub 组织/仓库管理员执行并回填记录：

1. 在 GitHub org `mixlab` 创建团队：repo-admins、platform-core、contract-committee、release-engineering、security-reviewers、admin-team、cutter-team、smart-team；每个团队至少 2 名成员（含 backup owner）。
2. 邀请并确认成员：产品负责人、平台负责人、发布负责人、安全负责人；离职/转岗需在 1 个工作日内更新团队。
3. 仓库分支保护（三仓分别设置）：Require a pull request before merging；Require review from Code Owners；Dismiss stale pull request approvals when new commits are pushed；Require status checks（typecheck / test / release:check）；Require conversation resolution；禁止直接 push main/release 分支。
4. 保护必须覆盖分支的模式：main、release/*、codex/* 发布分支（至少 release 分支必须受保护）；tag 保护（release 标签仅 release-engineering/repo-admins 可创建）。
5. 确认 GitHub 能解析 CODEOWNERS 中的团队（PR 页面出现 “Invalid owner” 即为未建团队）；若组织使用 GitLab/Bitbucket，需按对应平台语法与权限模型另配（本地 git 不执行 CODEOWNERS）。
6. 安全项：GitHub Environments/Secret 权限、Actions 权限最小化、Docker/GHCR 推送权限、Windows 签名证书访问权限归 repo-admins + release-engineering 双人控制。
7. 记录生效证据：在 progress/ROUND6-GATE.md（或等价发布记录）附上分支保护截图/JSON 导出与团队列表；未生效前，CODEOWNERS 仅是评审约定，不得对外宣称已强制执行。

## 4. 评审与合并规则

- 每个 PR 至少 1 名路径 owner 批准；契约/发布路径至少 contract-committee 或 platform-core 其一 + release-engineering（或按 CODEOWNERS 组合）。
- 安全敏感路径至少 security-reviewers 一人批准；发布前由 release-engineering 复核 release:check 与清单。
- 变更跨仓（如契约修改需三仓同步）必须在 PR 描述中列出：契约版本、三仓同步提交/哈希、兼容性矩阵、回滚方式；契约委员会按 07 的流程审批。
- 紧急变更（hotfix）走 07 的紧急通道：双人批准 + 24h 内补 RFC/复盘；紧急通道不得绕过 release:check 的事实性检查。
- 禁止事项：直接 push 受保护分支、以本地 dirty 工作区产物作为发布依据、未经契约委员会批准修改 contracts 语义、在同一 PR 混入 UI/认证/缓存/Windows 打包等不相关高风险批次（参见 docs/operations/git-checkpoints.md 的 checkpoint 规则）。

## 5. 跨仓同步机制（过渡期，直到 08 的拆分方案落地）

1. 权威源：以 mixlab 仓的 packages/contracts 为唯一源；cutter/smart 仓为**只读镜像**，同步由 Lead/契约委员会执行，PR 中附三仓哈希。
2. CI 检查（后续任务）：在三仓新增 `contracts:check`，比较本仓 contracts 源文件 sha256 与 versions.json 中记录的同步哈希，不一致则 fail；本地可先由 release-manifest 工具输出清单。
3. 其他共享包（protocol/library-format/service-clients）同样按“平台源 + 产品镜像”管理；library-fs 已出现三仓内容漂移，08 给出收敛方案（先 monorepo 收敛，再平台仓拆分）。
4. 每季度由 platform-core 输出一次三仓共享文件一致性报告（哈希 + 差异清单），作为契约委员会输入。

## 6. 渐进落地阶段

| 阶段 | 内容 | 门禁 | 回退 |
|---|---|---|---|
| G0（本文，无代码行为变化） | CODEOWNERS 模板 + 治理/委员会/拆分评估文档 | 文档评审通过；CODEOWNERS 语法在 GitHub 验证 | 删除 CODEOWNERS/文档，不改代码 |
| G1（需 GitHub 管理员） | 建团队、开分支保护、启用 CODEOWNERS、CI 状态检查 | 团队/分支保护截图；一次演练 PR 强制 owner 评审 | 关闭分支保护（记录原因） |
| G2 | 三仓 contracts hash 校验、release:check 纳入 required checks | CI 绿 + 清单一致 | 移除新增 required check |
| G3 | 按 08 的方案收敛为 monorepo（或决定拆分） | 契约委员会 + repo-admins 批准，Round7 计划 | 保留三仓分支与 tag 作为只读回退点 |

## 7. 待用户/组织管理员确认事项（汇总）

- GitHub org 是否存在 `mixlab` 及团队命名/成员；若命名不同，CODEOWNERS 需同步替换（三仓同批）。
- 受保护分支范围与 required checks 清单（typecheck/test/release:check 是否都设为 must-pass；Windows 构建是否要求 required）。
- 是否允许平台仓/产品仓在 Phase 3 拆分（08 的建议需要 repo-admins 与产品负责人共同确认）。
- 安全评审团队人选与双人批准流程、紧急变更的值班/升级路径（07）。
- 发布 tag 权限与签名证书/密钥托管方式（release-engineering 与 repo-admins 双人控制）。
