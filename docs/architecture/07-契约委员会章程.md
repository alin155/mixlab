# 07 · 契约委员会章程（Contract Committee Charter）v1

> 状态：Round6 起草，2026-10-27。本章程管理**跨边界契约**的变更审批，不替代产品需求评审或发布评审。
> 相关文档：[06 仓库与团队治理](./06-仓库与团队治理.md)、[08 仓库拆分评估](./08-仓库拆分评估.md)、[Cutter Release Protocol](./cutter-release-protocol.md)、[规格追溯](../spec-traceability.md)、[发布列车](../operations/release-trains.md)、[回滚 Runbook](../operations/rollback-runbook.md)。

## 1. 目的与范围

契约委员会（下称“委员会”）保证三端（管理端、剪辑端、智能剪辑端）与平台服务之间的数据/API/错误/事件协议可以**独立演进且不互相破坏**。

纳入契约范围（改这些必须走本章程）：

1. `packages/contracts/src/**`：`CONTRACT_VERSION`、`CONTRACT_ERRORS`、CapabilityTableV1、ReleaseManifestV2、EventEnvelopeV1、Local Agent v1。
2. `packages/library-format/src/**`：公共库/发布目录的磁盘格式与路径协议。
3. `packages/service-clients/src/**`：身份/事件/发布服务的客户端协议（默认关闭 flag 的契约）。
4. `packages/protocol/src/**` 与 `packages/runtime-config/src/**` 中被三端共享的协议常量/配置键。
5. `scripts/release/versions.json` 中的契约/库格式版本与兼容矩阵字段；`release-manifest` 生成器的兼容性判定逻辑。
6. `docs/architecture/cutter-release-protocol.md` 与 `docs/architecture/admin-architecture-v1-requirements-traceability.md` 中对外承诺的协议条目。

不纳入：产品内部实现细节、UI 文案、单端内部数据库 schema（除非跨端读写）、feature flag 的默认值（归产品/Release 评审，但 flag 的**契约语义**归委员会）。

## 2. 成员与表决

| 角色 | 来源 | 职责 |
|---|---|---|
| 主席（Chair） | platform-core 指定，任期 6 个月可续 | 组织评审、裁决僵局、签署版本决议、紧急通道第一批准人 |
| 平台代表 ×1~2 | platform-core | 兼容性检查、共享包影响面 |
| 产品代表 ×3 | admin-team / cutter-team / smart-team 各 1 | 代表客户端兼容与发布窗口 |
| 发布工程代表 ×1 | release-engineering | 发布列车、清单/版本、回滚可行性 |
| 安全代表 ×1 | security-reviewers | 认证/令牌/错误信息泄漏边界 |
| 记录员（Secretary） | 轮值 | RFC 编号、决议记录、行动项跟踪 |

表决规则：

- 常规变更加法（见 §3）：**至少 2 票赞成且无有效否决**即通过；参与表决人数达到 4 人（含主席或代理）为有效。
- 破坏性变更（见 §3 禁止项）：默认否决；如确需破坏性升级，需要**全体产品代表一致 + 主席 + 发布工程**同意，并走契约 major 版本与迁移/回滚方案评审。
- **否决权**：任一产品代表可以以“客户端兼容性证据不足”为由否决，必须给出可验证理由（具体客户端版本/场景/失败模式）；被否决 RFC 需补充证据后重新提交。主席可在 5 个工作日内组织复议，复议仍僵持则升级到工程负责人（Lead/技术负责人）裁决并记录。
- 回避：RFC 涉及某成员所在团队产品时，该成员可参与讨论但不计入赞成门槛（安全/主席除外）。

## 3. 版本与兼容规则（additive-only）

`CONTRACT_VERSION`（当前 1.0.0）采用 `MAJOR.MINOR.PATCH`：

- **MAJOR**：破坏性变更（仅在本章程 §2 全体同意 + 迁移方案下允许）。
- **MINOR**：纯加法（新增字段/新增错误码/新增 capability/新增可选端点），旧客户端必须能忽略。
- **PATCH**：文档/测试修正、修复不明显违背既有语义的 bug；不得改变字段含义。

允许（additive）：

- 新增可选字段、新增错误码（`CONTRACT_ERRORS` 只增不删、含义不变）、新增 capability feature flag（旧客户端 `=== true` 才启用）、新增可选端点/新版本路径（`/api/v1/*` 与旧 `/api/admin/*` 并存）。
- 现有字段类型不变前提下的约束放宽（如限制值上调），需在 RFC 中说明上限与客户端行为。

禁止（breaking，除非 §2 破坏性流程）：

- 删除/重命名字段或错误码；改变错误码的 HTTP 状态/可重试语义；改变字段类型、单位、精度或默认值含义；把可选字段改必填；改变发布指针/库目录布局的读取规则；让 `capabilities` 中已承诺的 feature 无提示地降级。

每个 RFC 必须包含**兼容性矩阵**：三端当前版本 × 新契约 = 可读/可降级/不可用 的明确结论；不得以“应该没问题”代替证据。

## 4. RFC 流程

状态机：`draft → review → approved → implemented → released → retro`（任何阶段可 `withdrawn`/`rejected`）。

1. **draft**：提出人写 RFC（模板见 §5），先在三仓任一 `docs/architecture/rfc/` 下开分支草稿（目录未建前可放 PR 描述，批准后归档到本仓 docs/architecture/）；不直接改 contracts 代码。
2. **review**：RFC 提交给委员会（GitHub Discussion/Issue + 委员会周会）。材料必须含：变更动机、契约 diff、加法证据、兼容性矩阵、三仓同步与发布计划、回滚方式、测试计划（contracts.test.ts/各端契约测试）。
3. **approved**：委员会按 §2 表决；记录决议编号与条件（如“需先有 client 0.19.0 兼容测试”）。
4. **implemented**：实现 PR 必须：更新 `packages/contracts/src/*` 与 `contracts.test.ts`；同步三仓 hash（或按 08 拆分后更新平台包版本）；更新 `scripts/release/versions.json` 契约版本与兼容矩阵；更新 capabilities/错误注册表（如涉及）；引用 RFC 编号。
5. **released**：随发布列车发布；release notes 标注契约版本与最低客户端版本；旧版本保持可用（见 §3）。
6. **retro**：发布后 5 个工作日内复盘兼容性问题；有兼容事故则冻结契约一周并强制补测。

时限：常规 RFC 评论窗口 3 个工作日、委员会决议 5 个工作日；Fast-track（低风险加法）1 个工作日（主席 + 1 产品代表 + 发布工程书面同意，无需开会）；紧急通道见 §6。

## 5. RFC 模板（最小字段）

- RFC 编号/标题/作者/日期/目标版本（CONTRACT_VERSION 或 release train）。
- 问题与动机（失败场景、影响客户端）。
- 契约变更清单（文件/字段/错误码/capability；diff 链接）。
- 兼容性矩阵（三端版本、旧客户端行为、降级路径）。
- 三仓同步与发布计划（镜像 hash、发布列车、flag 默认值）。
- 测试计划（contracts.test.ts、各端契约/客户端测试、E2E）。
- 回滚方案（按 docs/operations/rollback-runbook.md 的哪一节；是否能仅回滚 flag）。
- 风险与开放问题、委员会决议记录（编号、日期、反对/弃权、条件）。

## 6. 会议节奏与紧急通道

会议：

- 活跃开发期：每周一次 30 分钟（与发布列车合并窗口对齐；UTC 周会可在三端时区轮换）。
- 稳定期：每两周一次；无 RFC 时可取消并在异步频道记录。
- 发布列车冻结期：发布前 48 小时不开新 RFC（紧急通道除外）。

异步：RFC 评论在 GitHub；决议摘要与行动项当周写入本仓（本期可附在本文“附录 A：决议记录”或 release notes；后续建 docs/architecture/decisions/ 时迁移）。

紧急变更通道（仅用于已发生的生产兼容故障/安全事故，或客户端即将发布被阻塞）：

1. 触发者：值班 release-engineering 或 product owner，说明事故等级、影响范围、拟改契约 diff。
2. 批准：**双人批准**——主席（或平台代表代理）+ 发布工程代表；安全类再加 security-reviewers；批准记录写入 GitHub Issue/PR（含时间戳）。
3. 约束：紧急变更仍必须是**加法**；若必须 breaking，仅允许“回滚到上一契约版本 + 客户端回滚”，不允许前向 breaking。
4. 时限：24 小时内补 RFC/复盘；若 24 小时内未补，冻结下一次发布列车并升级到工程负责人。
5. 复盘必须回答：为何未在常规流程发现、兼容测试缺口、如何补测、是否需回滚已发布客户端。

## 7. 契约测试与 CI 门禁（过渡期）

- 权威测试：`packages/contracts/src/contracts.test.ts`（版本/错误注册表/能力表/发布清单/事件/本地 agent 不变量）；修改契约必须新增或更新测试断言。
- 三仓一致性：过渡期由平台在 CI 加 `contracts:check`（比较 contracts/library-format/service-clients 源文件 sha256 与 `scripts/release/versions.json` 记录）；不一致即 fail（详见 06 §5）。
- 发布门禁：`node scripts/release/release-manifest.mjs --check`（版本表/CONTRACT_VERSION 一致性）+ 三仓 typecheck + 全量测试；由 release-engineering 在发布列车执行。
- 客户端兼容证据：三端各保留至少一个“旧客户端契约读取”测试（如旧 cutter 读取新封存发布、旧 admin-web 读取 additive 字段）；E2E 兼容证据随 release train 归档到 docs/acceptance/。
